# Публикация Alem Practice

Сейчас проект подготовлен для одного постоянно работающего Node.js-сервера с постоянным диском. Размещение кода на GitHub само по себе не публикует сайт. GitHub Pages не запускает сервер регистрации и базу данных.

## Что понадобится

- Сервер/VPS или Node.js-хостинг с постоянным диском, Node.js 22.14+ и HTTPS.
- Домен и HTTPS-прокси перед приложением.
- Одна запущенная копия приложения и одна SQLite-база на диске этого сервера.

Не используйте временную файловую систему serverless-функций для SQLite: аккаунты должны сохраняться между перезапусками. Несколько независимых копий с разными файлами SQLite не разделяют пользователей. Для масштабирования нужно отдельно перенести схему и данные в общую СУБД.

## Развёртывание на Linux-сервере

1. Получите репозиторий и перейдите в `alem-practice`.
2. Создайте постоянный каталог, например `/var/lib/alem-practice`, доступный только пользователю приложения. Если переносите существующую базу, остановите приложение, сделайте резервную копию и скопируйте базу в этот каталог. Пустая база означает новые аккаунты, а не перенос старых.
3. Создайте `.env` на сервере; не отправляйте его в GitHub:

```dotenv
DATABASE_URL="file:/var/lib/alem-practice/app.db"
APP_URL="https://practice.example.org"
APP_ORIGINS=""
AI_MODE="mock"
```

Замените домен своим. Если нужен второй адрес, перечислите его точный HTTPS-origin в `APP_ORIGINS`, без `*`. Выберите один основной адрес для ссылок; cookie отдельных доменов не общие.

4. Установите зависимости, примените миграции и соберите приложение:

```bash
npm ci
npm run db:generate
npm run db:migrate
npm run db:seed
npm run build
npm start
```

Приложение слушает `127.0.0.1:3000`. На этом же сервере настройте HTTPS-прокси вашего хостинга на этот адрес. Например, при установленном Caddy и домене, уже направленном на сервер, Caddyfile:

```text
practice.example.org {
    reverse_proxy 127.0.0.1:3000
}
```

Это пример конфигурации, не автоматическая установка. Откройте в инфраструктуре порты HTTPS/HTTP для прокси; сам Node.js оставьте на loopback. Основа схемы: [Next.js Self-Hosting](https://nextjs.org/docs/app/guides/self-hosting) и [Caddy HTTPS quick-start](https://caddyserver.com/docs/quick-starts/https). Не используйте `start:lan` для публичного HTTPS-сервера: команда предназначена для локальной демонстрации и меняет `APP_URL` на HTTP.

5. Настройте постоянный запуск через менеджер процессов хостинга/systemd: рабочая папка — `alem-practice`, команда — `npm start`, пользователь — владелец базы. Секреты храните в окружении сервиса или `.env` с ограниченными правами. Приложение должно автоматически запускаться после перезагрузки.
6. Откройте HTTPS-адрес, зарегистрируйтесь и сохраните профиль. С другого устройства войдите с тем же логином. Перезапустите сервер и убедитесь, что профиль сохранился. Проверьте, что cookie `alem_session` имеет HttpOnly, SameSite=Lax, Secure.

## Обновления и резервная копия

Перед изменением схемы остановите приложение и сохраните копию SQLite-файла вне каталога новой версии. Получите обновления, повторите установку, генерацию Prisma, миграции и сборку; затем запустите сервер с прежним `DATABASE_URL`. Регулярно делайте резервные копии и проверяйте восстановление. Не удаляйте постоянный диск при очередном развёртывании.

## Ограничения текущего MVP

Восстановление/смена пароля, приглашения в команду, модерация и распределённая защита от массовых атак ещё не реализованы. Вход ограничен по логину и общему счётчику экземпляра приложения; для открытой аудитории настройте также лимиты на уровне прокси и наблюдение за ошибками. Демо-кейсы и датасеты синтетические.

Публичный хостинг в рамках этого обновления не создавался. Эта инструкция описывает подготовленную схему запуска.
